## Ключевое архитектурное решение: цикл interaction и снапшот состояния

**Команды делятся на два вида:**

- *мгновенные* — меняют состояние кадра и не ждут игрока: `scene`, `show`, `hide`, `music`,
  `sfx`, `set`, `jump`;
- *требующие interaction* — останавливают выполнение до действия игрока: `say`, `choice`.

Цикл движка: применять мгновенные команды подряд, пока не встретится требующая interaction;
на ней остановиться и отрисовать кадр. Один клик игрока = один `advance()` = проход до
следующей команды, требующей interaction.

Это в точности главный цикл Ren'Py (`run_context` → `Interface.interact`), тот же цикл у ink
(`Continue()` пока `canContinue`, затем `currentChoices`). Терминология взята оттуда же.

### Сейв — это снапшот, а не реплей

```ts
type SaveData = {
  version: 1;                      // формат сейва
  position: { sceneId: SceneId; step: number }; // step — в скомпилированной программе сцены
  sceneHash: string;               // хэш программы сцены: менялась ли сцена после сохранения
  vars: Record<VarName, VarValue>;
  stage: {
    background: BackgroundId | null;
    sprites: Array<{ tag: CharacterId; emotion: EmotionId; at: SpritePosition }>;
  };
  audio: { music: MusicId | null };
  savedAt: number;
};
```

**Загрузка:** восстановить `vars`, `stage` и `audio` из снапшота, поставить позицию, затем
выполнить **одну** команду по индексу `position.step` — она гарантированно `say` или `choice`.
Никакого проигрывания истории.

**Сцена изменилась после сохранения** (правка сценария сдвинула шаги) — `sceneHash` не
совпадёт: тогда сцена начинается с начала с переменными из сейва. Игрок теряет максимум одну
сцену и никогда не попадает в середину чужой реплики (решение ревью этапа 2).

**Автосейв — в начале каждой команды, требующей interaction.** Дословно как в Ren'Py:
*«saving occurs at the start of a statement»*.

Первая редакция плана предлагала вместо этого реплей: проиграть сцену от шага 0 до
сохранённого. Разбор показал, что так не делает никто — ни Ren'Py, ни Pixi'VN, ни ink.
Реплей экономит четыре поля в сейве, но требует детерминированности всех команд и
принципиально не восстанавливает путь исполнения: после `jump` из середины другой сцены
проигрывать нечего. Документация Ren'Py про это прямо: *«Ren'Py only saves the current
statement, and the statement it needs to return to. It doesn't remember how it got there»*.

**Бонусы снапшота:** `stage` — plain data в несколько полей, поэтому rollback на реплику
назад позже стоит просто «держать N последних снапшотов», а лог диалога — «держать
прочитанные реплики». Оба пункта из списка «не в 0.1» становятся почти бесплатными.

**Цена:** сейв вырос с 4 полей до 6. Поле `position` сделано объектом, чтобы позже принять
`callStack`, когда появятся вызываемые подсцены (у Ren'Py стек вызовов лежит в сейве).

### Переменные объявляются с дефолтами

```ts
export const variableDefaults = { metAnna: false, trust: 0 } as const;
type VarName = keyof typeof variableDefaults;
```

При загрузке: `{ ...variableDefaults, ...save.vars }`. Старый сейв, сделанный до появления
новой переменной, не ломает игру — переменная получит дефолт.

Это механика `default` из Ren'Py, где рекомендация звучит буквально: *«It is highly
recommended to `default` every variable in your game that is susceptible to change»*.
Заодно это закрывает миграцию сейвов, для которой раньше было только поле `version`.

## Структура репозитория

```
engine/       движок — отдельно от приложения: types, state, program, interpreter, save;
              свой tsconfig без DOM, публичный API — engine/index.ts. Звук — эффектами,
              играет их приложение (shared/lib/audio.ts поверх howler)

src/
  main.tsx    точка сборки: реестр сцен из content/ + движок → RootStore
  app/        App, сторы (RootStore, UiStore, GameStore, SettingsStore), ThemeProvider,
              глобальные стили
  pages/      MainMenuPage, GamePage
  widgets/    Stage, DialogueBox, GameHeader, SettingsOverlay, ConfirmDialog, NoticeToast
  features/   advance-dialogue (и горячие клавиши), make-choice, change-settings,
              switch-language
  entities/   background, character (слои кадра)
  shared/     ui (Button, PillButton, IconButton, Tooltip, Modal, Slider), lib (units, uiScale,
              useTypewriter, storage, audio, stores), config, i18n
  content/    ids, speakers, variableDefaults, фабрики (dsl), scenes, __dev__/ тестовый контент
  assets/     backgrounds/, characters/, music/, sfx/
```

**Правила границ** (первые три проверяет `no-restricted-imports` в oxlint, остальное —
руками):

- `engine/` не импортирует ничего из `src/`: ни FSD-слоёв, ни `content/`. Реестр сцен
  передаётся снаружи, при загрузке приложения (`main.tsx`).
- `engine/` — чистый TypeScript: без React, без MobX, без DOM (последнее проверяет
  `tsconfig.engine.json`). MobX-обвязка — `GameStore` в `app/stores/`.
- `src/` импортирует движок только через публичный API: `from '@engine'`.
- FSD-слои импортируют только вниз (`app → pages → widgets → features → entities → shared`);
  сторы слоям ниже `app/` доступны через `AppStores` из `shared/`.
- О сюжете знает только `content/`; подключает его к движку только точка сборки.

Это то же разделение, что у Ren'Py между execution-слоем и display-слоем: исполнение меняет
логическое описание кадра, отрисовка отдельно превращает его в пиксели.

## Типы контента

```ts
type SpritePosition = 'left' | 'center' | 'right';
type LocalizedText = string | { $key: string };

// Движок не знает конкретных id: по умолчанию всё — string. content/ сужает параметр
// под свои реестры, и опечатка в id становится ошибкой компиляции.
type Ids = { scene: string; background: string; character: string; emotion: string;
             speaker: string; music: string; sfx: string;
             vars: Record<string, VarValue> }; // тип переменных целиком — для `when`

type Command<I extends Ids = Ids> =
  // мгновенные
  | { type: 'scene'; background: I['background'] }
  | { type: 'show'; tag: I['character']; emotion: I['emotion']; at?: SpritePosition }
  | { type: 'hide'; tag: I['character'] }
  | { type: 'music'; asset: I['music'] | null; ifChanged?: boolean }
  | { type: 'sfx'; asset: I['sfx'] }
  | { type: 'set'; name: VarName<I>; value: VarValue }
  | { type: 'jump'; scene: I['scene'] }
  // требуют interaction
  | { type: 'say'; speaker?: I['speaker']; text: LocalizedText } // без speaker — рассказчик
  | { type: 'choice'; prompt?: { speaker?: I['speaker']; text: LocalizedText }; // подпись
      options: ChoiceOption<I>[] };

type ChoiceOption<I extends Ids = Ids> = {
  text: LocalizedText;
  when?(vars: Vars<I>): boolean; // методом, а не свойством: иначе ломается вариантность
  then: Command<I>[];            // блок; может закончиться jump в другую сцену
};
```

**Ветвление — два механизма в одной модели.** Крупные ветки — отдельные сцены, короткие
реакции — блоки внутри варианта, после которых выполнение продолжается за развилкой (как
`menu` в Ren'Py). Переход в другую сцену — это блок из одного `jump`:

```ts
choice([
  option('Пойти в лес', goTo('forest')),       // goTo = блок [jump('forest')]
  option('Остаться', [say('anna', 'Тогда подождём здесь.')]),
]),
say('anna', 'Темнеет...'),                     // сюда сходятся блоки-реакции
```

При регистрации сцена разворачивается из дерева в **плоскую программу** с внутренними
переходами — как указатели `next` у statement'ов Ren'Py. Поэтому позиция остаётся
`{ sceneId, step }`, а интерпретатор — простым циклом.

**Сценарий пишется фабриками** из `content/`: `scene('room')`, `show('anna', 'happy', 'left')`,
`say('anna', '…')`, `narrate('…')`, `goTo('forest')`, `choice([...])`, `option(...)`.
Фабрика заодно проверяет то, что тип-объединение не выразит: эмоция `happy` есть именно у
Анны.

**Конец сцены без `jump`** — конец игры и возврат в меню, как в Ren'Py при пустом стеке
вызовов.

**Недоступный по `when` вариант скрывается** — как в Ren'Py
(`config.menu_include_disabled = False`), чтобы не спойлерить. Движок отдаёт флаг
`available`, так что показ серым — одна настройка UI. **Выбор, у которого недоступны все
варианты, пропускается** — тоже как в Ren'Py (этап 4).

**Подпись у выбора** — реплика, которая видна, пока игрок выбирает: `choice(say('mila',
'Куда пойдём?'), [...])`, как реплика внутри `menu` в Ren'Py. Она часть команды `choice`, а не
«предыдущая реплика»: сейв на развилке хранит позицию на выборе, а не путь к нему, и подпись
после загрузки та же (этап 4).

**Чёрный экран** — обычный фон `black` в контенте: `scene('black')`, движок его не выделяет.

Четыре конвенции, взятые у Ren'Py:

1. **`scene` очищает кадр и ставит фон, `show` добавляет спрайт поверх.** Раньше в плане была
   одна команда `background`, которая смешивала эти операции.
2. **Автозамена по тегу.** `show anna sad` заменяет ранее показанную `anna` — персонаж
   опознаётся тегом, а не полным именем ассета. Поэтому смена эмоции не требует `hide`, и
   `hide` вообще нужен редко.
3. **Позиции — фиксированный набор `left / center / right`**, а не пиксели. Это `at left`
   из Ren'Py; пиксельные координаты в контенте — путь к тому, что арт нельзя заменить.
4. **`ifChanged` у музыки** — не перезапускать трек, если он уже играет. Критично при
   загрузке сейва внутри той же сцены: иначе музыка дёрнется с начала.

Плюс два приёма для автокомплита:

- id фонов, персонажей, музыки выводятся из реестров в `content/` и подставляются в
  `Command<ContentIds>` — опечатка в имени становится ошибкой компиляции;
- `LocalizedText` допускает и строку, и ключ; движок достаёт текст через `resolveText()`,
  который в 0.1 просто возвращает строку.

**Движок — чистое ядро.** Функции над plain data: состояние `{ position, vars, stage, audio }`
на входе и выходе, без MobX и React. `GameStore` в `app/` держит это состояние и вызывает
движок; тесты движка обходятся без MobX, а сейв — это то же состояние.

**Случайности в сюжете нет** — детерминированный генератор случайных чисел не нужен.

## Сторы

| Стор | Что держит | В сейве |
|---|---|---|
| `GameStore` | состояние движка целиком (`position`, `vars`, `stage`, `audio`) + текущее interaction; вычисляемые `stage` и `line` | да — `state` и есть снапшот |
| `SettingsStore` | громкости по каналам, скорость текста | да, отдельным ключом |
| `UiStore` | активный экран, открыт ли оверлей настроек | нет |
| `AudioService` | howler, текущий трек | нет, не observable |

Три независимых хранилища, как в Ren'Py: сейв (точка в игре), настройки (переживают все
прохождения), и — позже — `persistent` для прочитанных реплик и достижений.

`StageStore` и `DialogueStore` из первой редакции не понадобились: при чистом ядре это
вычисляемые поля `GameStore` (решено на этапе 2). Состояние набора текста (`isRevealing`) —
забота UI на этапе 3.

**Доступ к сторам из слоёв ниже `app/`** — тем же приёмом, что тема: в `shared/` пустой
интерфейс `AppStores` и хук `useStores()`, `app/` расширяет интерфейс через `declare module`.
Импортов снизу вверх нет, типы полные.

## Как мы работаем

1. **Небольшие атомарные шаги.** Не этап целиком, а один шаг внутри этапа: одна проверяемая
   вещь за раз. После каждого шага я останавливаюсь и отчитываюсь, что сделано и что
   проверить.
2. **Коммитит Павел.** Один шаг = один коммит с его стороны. Поэтому шаг должен быть
   осмысленным сам по себе: не оставлять проект в нерабочем состоянии между шагами.
3. **Ключевые решения — вопросом до реализации.** Всё, что повлияет на структуру или на
   последующий код, я выношу вопросом, а не показываю готовым. Мелкие обратимые вещи решаю
   сам и просто называю их в отчёте.
4. **Открытые вопросы закрываем по ходу**, а не квизом заранее. Помеченные **(квиз)** в
   задачах поднимаю в тот момент, когда упираюсь в них, — и записываю ответ в задачу.
5. **Расхождения с планом фиксируются.** Если реальность разошлась с планом, правится план,
   а запись идёт в [tasks/progress.md](./tasks/progress.md).

Готово, когда: `npm run dev` открывает страницу, `lint`, `typecheck`, `test`, `build` проходят.

### Этап 1. Каркас: кадр, тема, экраны · [задача](./tasks/01-shell.md)

- Тема: цвета, шрифты, z-индексы, длительности анимаций. Плюс токены, специфичные для
  новеллы — их список подсказал `gui.rpy` из Ren'Py: высота диалогового окна, позиция реплики,
  позиция и размер имени говорящего отдельно от размера реплики, отступы вариантов выбора.
- Глобальные стили: reset, чёрный фон под letterbox, запрет выделения текста там, где оно
  мешает клику.
- `Stage`: контейнер 1920×1080, `transform: translate(…) scale(min(vw/1920, vh/1080))` через
  `useStageFit` на `ResizeObserver`; смещение привязано к физическому пикселю, без
  `will-change`. Слои кадра: фон → спрайты → UI → оверлей. Окно меньше 960×540 — заглушка
  «окно слишком маленькое».
- Корневой стор + провайдер + `useStores()`. `useStores()` используется только в `app/`,
  страницы получают колбэки пропсами.
- `MainMenuPage` **внутри кадра** («Новая игра»; «Продолжить» и «Настройки» неактивны) →
  `GamePage` с пустой сценой.

Готово, когда: меню открывается, «Новая игра» ведёт на пустой кадр 16:9, ресайз и
фуллскрин не ломают пропорции.

### Этап 2. Ядро движка: типы и интерпретатор · [задача](./tasks/02-engine-core.md)

- `engine/` (корневая папка, вне `src/`): типы `Command<I>` с дженериком по id, `ChoiceOption`
  с блоком, `resolveText`; чистые функции над состоянием — мгновенные команды с автозаменой
  по тегу, `scene` очищает спрайты, эффекты `music` / `sfx`; реестр сцен с плоской программой
  (включая разворот блоков `choice`) и проверкой целей `jump`; интерпретатор с лимитом шагов,
  конец сцены = конец игры. Без MobX, React и DOM.
- `content/`: id, говорящие, `variableDefaults`, фабрики команд, демо-сцена.
- `shared/`: `AppStores` + `useStores()` по приёму темы; `app/`: `GameStore` держит состояние
  движка, «Новая игра» запускает демо-сцену.
- Тесты Vitest: мгновенные команды применяются подряд; на команде с interaction выполнение
  встаёт; `show` с тем же тегом заменяет спрайт, а не добавляет второй; `scene` очищает
  спрайты; `jump` переключает сцену; снапшот состояния сериализуется и восстанавливается
  без потерь.

Готово, когда: `npm test` зелёный. Визуально на этом этапе ещё ничего нового — проверка
тестами, это осознанно.

### Этап 3. Рендер сцены — первый играбельный билд · [задача](./tasks/03-rendering.md)

- `entities/background`, `entities/character` — слои; позиции спрайтов `left / center / right`
  — колонки из дизайна. Файлы за id объявлены в `content/assets.ts` (как `image` в Ren'Py), а
  `GameStore` отдаёт UI готовые URL и имена (`background`, `sprites`, `line`).
- `widgets/dialogue-box` — панель из дизайна: портрет, имя, текст с кареткой, системные кнопки
  (пока заглушки). Typewriter через `useTypewriter` на rAF. Реплика с самого начала занимает
  финальную высоту — приём тега `{done}` из Ren'Py; высота панели постоянная.
- `features/advance-dialogue` — клик по кадру (кроме системных кнопок) и клавиши идут в
  **один** `requestAdvance()`: печатается — дописать, дописано — следующий шаг.
- Горячие клавиши: Space / Enter — дальше (автоповтор гасится), Esc — меню. Обработчик —
  в `features/advance-dialogue` на экране игры.
- Демо-арт из дизайна (WebP): фон комнаты и персонаж; второй фон — SVG-заглушка.

Готово, когда: линейная сцена проходится от начала до конца мышью и с клавиатуры, текст
печатается, клик доводит реплику.

### Этап 4. Выборы, переменные, переход между сценами · [задача](./tasks/04-choices.md)

- `features/make-choice` — варианты текстовыми строками в панели реплики, под подписью
  выбора. Подпись печатается как обычная реплика; когда игрок её прочитал (клик), она
  отступает — приподнимается, тускнеет, обрезается до строки (полный текст — в тултипе) — и
  появляются варианты. Экрана выбора в дизайне нет, это черновик.
- Доработка UX по ходу этапа: системные кнопки — иконки с тултипами в правом верхнем углу
  панели; имя и портрет говорящего — на плашке поверх верхнего края панели; текст реплики
  всегда начинается в одном месте и идёт на всю ширину панели.
- Выбор варианта (`choose`) поверх готового с этапа 2 разворота блоков: `goTo` уводит в
  другую сцену, блок-реакция продолжает выполнение за развилкой; вложенные блоки. Подпись у
  выбора; выбор без доступных вариантов пропускается.
- Переменные с дефолтами и `set` готовы с этапа 2.
- Ветвящийся тестовый контент в `content/__dev__/` — в игру не входит, запускается на
  dev-сервере по `?dev=branching`, в прод-сборку не попадает.
- Тесты: выбор ведёт в нужную ветку, переменная влияет на доступность варианта.

Готово, когда: dev-сцена с ветвлением проходится оба раза по-разному.

### Этап 5. Save / Load · [задача](./tasks/05-save-load.md)

- `engine/save`: снапшот по схеме выше, `zod/mini`-схема на валидацию загруженного (кривой
  сейв прошлой версии не должен ронять игру), слияние с `variableDefaults`, миграция по
  `version`, хэш программы сцены. Хранилище — не в движке (там нет DOM), а
  `shared/lib/storage.ts`: `localStorage`, который никогда не бросает.
- Загрузка: восстановить снапшот → выполнить одну команду на `position.step`.
- Автосейв в начале каждой команды, требующей interaction. Один слот; кнопка «Сохранить»
  пишет в него же и говорит «Игра сохранена». Конец игры стирает сейв.
- «Продолжить» в меню активна, когда сейв есть.
- Тесты: сохранение → загрузка даёт то же состояние; сейв без новой переменной получает её
  дефолт; сейв с мусором отбрасывается, а не ломает игру.

Готово, когда: пройти половину сцены, обновить страницу, «Продолжить» — то же место, тот же
фон, тот же персонаж в той же эмоции и позиции.

### Этап 6. Аудио и настройки · [задача](./tasks/06-audio-settings.md)

- Аудио поверх **howler.js** — не в `engine/` (там нет DOM), а `shared/lib/audio.ts`: каналы
  `music` и `sound` (разделение из Ren'Py), кроссфейд 500 мс, `ifChanged`. Движок отдаёт
  эффекты, `GameStore` проигрывает их и восстанавливает музыку из сейва. Автоплей: музыка
  стартует из клика, на отказ — повтор на `unlock` howler'а.
- `SettingsStore` + окно настроек: громкость по каналам (общая × канал), скорость текста в
  символах в секунду (0 — мгновенно), **язык**; хранится ключом `ots:settings`, отдельно от
  сейва. Esc в игре и шестерёнка открывают окно (в нём и «Главное меню» — как game menu
  Ren'Py), в меню — кнопка «Настройки». В `UiStore` — `overlay` (окно поверх экрана).
- Подтверждение «Новой игры», когда есть что продолжать (решение ревью этапа 5).

Готово, когда: музыка играет и не падает на политике автоплея, загрузка сейва внутри той же
сцены не перезапускает трек, ползунки влияют на звук и скорость печати немедленно.

### Этап 7. Полировка и сдача 0.1 · [задача](./tasks/07-polish.md)

- Fade-переход между сценами. Изменения кадра накапливаются и показываются одним переходом —
  как `show` в Ren'Py, который сам по себе не вызывает отрисовку. Длительность по умолчанию
  0.5 с, это стандарт жанра.
- Актуализация `README.md` и `CLAUDE.md`.
- Прогон `lint` / `typecheck` / `test` / `build`.
- Ревизия: что оказалось неудобным, что переносим в 0.2.

## Решения, принятые без отдельного вопроса

1. **Автосейв одного слота уже в 0.1.** Бриф относит автосейв в будущее, но кнопке
   «Продолжить» нужен хоть один сейв. Разбор показал, что автосейв на каждой команде с
   interaction — это ровно поведение Ren'Py, так что решение совпало со стандартом.
   Множественные слоты остаются в будущем.
2. **Плейсхолдер музыки** — короткий сгенерированный WAV-луп, чтобы аудио-система была на
   чём проверена.
3. **Fade-переход попал в 0.1** (этап 7). Единственная анимация.
4. **`noUncheckedIndexedAccess`** включён.
5. **`CLAUDE.md`** создаётся на этапе 0: команды, конвенции, правила границ слоёв.
6. **Язык кода** — английский: имена, коммиты, комментарии. Русский только в тексте игры и
   в документах в `.claude/`.
7. **Канал `sfx` есть в типах, но в контенте 0.1 не используется.** Добавить канал в howler
   сразу дешевле, чем переделывать аудио-слой под второй канал потом.

## Риски

- **Резкость текста при `transform: scale`.** На нецелых коэффициентах текст может выглядеть
  чуть мягче. Альтернатива — верстать внутренности в единицах контейнера (`cqw`). Решаем по
  факту, на этапе 1.
- ~~**styled-components и свежий React.** Возможен конфликт peer-зависимостей; проверяем
  первым делом на этапе 0, откат — на React 18.~~ Снят на этапе 0: styled-components 6.4
  встал на React 19 без конфликта.
- **howler.js развивается медленно.** Библиотека проверенная и без зависимостей, но релизы
  редкие. Если упрёмся — слой `engine/audio` изолирует её, и переезд на Web Audio API
  затронет один файл. Это и есть причина не звать howler напрямую из UI.
- **Соблазн начать строить движок.** Бриф прямо это запрещает. Каждая абстракция в
  `engine/` должна быть нужна демо-сцене прямо сейчас. Разбор Ren'Py даёт длинный список
  соблазнов — контексты, NVL-режим, система screens, дельты в rollback. Всё это осознанно
  отброшено, см. [engine-research.md](./engine-research.md).
