# Разбор существующих движков визуальных новелл

Цель: не изобретать велосипед. Взять готовые решения там, где домен уже их выработал, и
осознанно отказаться от остального. Глубокий разбор — Ren'Py, как признанный эталон жанра.
Находки по остальным решениям зафиксированы ниже.

Влияние на план: см. раздел [Что меняется в плане](#что-меняется-в-плане).

## Обзор решений

| Решение | Стек | Лицензия / масштаб | Ценность для нас |
|---|---|---|---|
| **Ren'Py** | Python + SDL | Free, стандарт жанра, ~20 лет | Модель целиком. Кода взять нельзя, концепции — можно все |

| **TyranoScript / Tuesday JS** | JS, свой скриптовый язык / no-code | Живые, нишевые | Ничего существенного |
| **Naninovel** | Unity | Платный, не open-source | Только UX-референс |

## Ren'Py: глубокий разбор

### Слоёная архитектура

Пять слоёв с односторонними зависимостями:

```
Content   .rpy файлы и ассеты
Parsing   renpy.parser / renpy.lexer  →  AST (renpy.ast.Node)
Execution renpy.script.Script + renpy.execution.Context  →  состояние рантайма
Display   Displayable  →  дерево Render
Backend   OpenGL (GL2Draw) или software (SWDraw)
```

Поперёк слоёв идут сервисы: `renpy.config`, `renpy.loader`, `renpy.rollback`.

Главное здесь: **исполнение скрипта не знает о рендеринге**. Statement'ы просто меняют
`SceneLists` — логическую структуру того, что должно быть на экране. Display-слой отдельно
превращает эту структуру в пиксели.

Это ровно то разделение, которое бриф требует от `engine/` и UI: движок меняет описание кадра,
React отдельно его рисует.

### Цикл interaction — сердце движка

```
run_context():
    repeat node.execute() on current node
        until an interaction is required, or the context ends

Interface.interact():
    1. отрисовать текущий кадр (scene_lists.render())
    2. опросить события ввода, раздать их displayable'ам
    3. как только displayable вернул не-None — вернуть управление в цикл исполнения
```

То есть: statement'ы выполняются подряд, пока какой-нибудь не потребует взаимодействия;
тогда движок останавливается, рисует кадр и ждёт. Ответ игрока возвращает управление
в цикл исполнения.

**Это в точности та модель «мгновенные / блокирующие команды», которая была в плане.**
Единственное, что план назвал своими словами то, что в Ren'Py называется interaction.
Терминологию стоит подтянуть: блокирующая команда = команда, требующая interaction.

### Контексты и call stack

`Context` держит текущий node, стек кадров вложенных вызовов и `SceneLists`.
Контекстов может быть несколько (`renpy.game.contexts`), текущий — верхний.

- `jump` — переход без запоминания места возврата. «Нет способа вернуться туда, откуда
  прыгнул».
- `call` — переход с push'ем следующего statement'а в стек вызовов.
- `return` — pop стека. Если стек пуст — возврат в главное меню.

**Call stack сохраняется в файл сейва.** И важное ограничение: rollback работает и
сохраняется только в базовом контексте — «Rollback is only enabled in the base context, and
only the base context is saved».

Вывод для нас: если однажды понадобятся вызываемые подсцены (общие сценки, которые
используются из разных мест), стек вызовов придётся положить в сейв. Проектировать позицию
как одно `(sceneId, step)` — нормально для 0.1, но структуру стоит завести сразу как
`position`, чтобы потом добавить `callStack` без ломки формата.

### Слои и SceneLists

`SceneLists` раскладывает displayable'ы по слоям. Стандартные четыре:

| Слой | Назначение |
|---|---|
| `master` | фоны и спрайты персонажей — то, чем управляют `scene` / `show` / `hide` |
| `transient` | очищается в конце каждого interaction |
| `screens` | UI-слой (диалоговое окно, меню) |
| `overlay` | сверх всего, очищается при перезапуске interaction |

Внутри слоя элементы имеют тег и z-order.

### scene / show / hide и теги — ключевая конвенция

Имя изображения — это список компонентов через пробел: первый — **тег**, остальные —
**атрибуты**. `show mary happy`: тег `mary`, атрибут `happy`.

- **`scene`** — очищает слой целиком и показывает новое изображение. Используется для смены
  фона.
- **`show`** — показывает изображение на слое. **Если на слое уже есть изображение с тем же
  тегом, оно заменяется.** Поэтому смена эмоции — это просто `show mary sad`, без `hide`.
- **`hide`** — убирает по тегу. Нужен редко именно из-за автозамены.

Ещё одна деталь: сам `show` не вызывает отрисовку. Кадр обновится на следующем interaction
(реплика, пауза, переход). Это позволяет накопить несколько изменений и показать их одним
переходом.

- **`at`** — применяет трансформы. Готовые: `at left`, `at center`, `at right` — стандартные
  позиции спрайтов в жанре.
- **`with`** — применяет переход к изменениям кадра. `with dissolve`, `with None`
  (зафиксировать состояние без видимого перехода, чтобы следующие изменения ушли одним
  переходом).

### Character как объект и контракт с say screen

`say` имеет три формы: нарратив (одна строка, говорящего нет — работает через
встроенного персонажа `narrator`), явное имя + реплика, и объект `Character` + реплика.

`Character` настраивает: отображаемое имя, `who_color`, `what_prefix` / `what_suffix`
(например, обернуть реплику в кавычки), `image` — **связка персонажа с тегом спрайта**,
чтобы смена позы шла автоматически из реплики, и `interact` — требует ли реплика клика.

Контракт: `say` не рисует — он передаёт данные в screen, настроенный у персонажа. Один
statement, разная подача.

Режимы: **ADV** — одна реплика на экране за раз (норма для нашей игры), **NVL** — страница
текста, реплики накапливаются.

### Текстовые теги и typewriter

Разметка внутри строки реплики. Оформление: `{b}`, `{i}`, `{color}`, `{size}`.
Управление потоком:

| Тег | Что делает |
|---|---|
| `{w}` | ждать клика; с аргументом — ждать N секунд |
| `{p}` | закончить абзац и ждать клика |
| `{nw}` | не ждать клика, реплика сама снимается по завершении вывода |
| `{cps}` | скорость вывода в символах в секунду; с `*` — множитель текущей скорости |
| `{fast}` | всё до тега показать мгновенно |
| `{done}` | текст после не показывается — резервирует место, чтобы верстка не прыгала |

Typewriter — это `preferences.text_cps`, символов в секунду. Клик во время вывода
**мгновенно доводит остаток**, а не продолжает посимвольно. Именно так и было в плане.

Отдельно стоит отметить `{done}`: реплика занимает финальную высоту с самого начала, поэтому
диалоговое окно не дёргается по мере набора текста. Дешёвый приём, о котором сам бы не
подумал.

### define против default — решение проблемы миграции сейвов

- `define` — значение задаётся при инициализации, переменная считается константой. **В сейв
  не попадает** и не участвует в rollback.
- `default` — значение выставляется, только если переменной нет: при старте новой игры или
  после загрузки сейва, где её не было. **Участвует в сейве и rollback.**

Прямая рекомендация документации: *«It is highly recommended to `default` every variable in
your game that is susceptible to change»*.

Что это решает: старый сейв, сделанный до появления новой переменной, не ломает игру —
переменная получит дефолт при загрузке. И состояние не «протекает» между прохождениями.

Это готовый ответ на вопрос миграции сейвов, который в плане был закрыт только заготовкой
поля `version`.

### Сейв и rollback: снапшоты, а не реплей

Это главная находка разбора.

Ren'Py **не проигрывает скрипт заново**. Сейв — это снапшот состояния:

- текущий statement и тот, куда нужно вернуться;
- изменённые переменные store (pickle);
- показанные displayable'ы и трансформы;
- состояние screens и их переменных;
- состояние аудио;
- метаданные: имя, время, версия.

Прямая цитата: *«Ren'Py only saves the current statement, and the statement it needs to return
to. It doesn't remember how it got there»* — путь исполнения не сохраняется принципиально.

Сохранение происходит **в начале каждого statement'а, взаимодействующего с игроком**:
*«saving occurs at the start of a statement»*.

Rollback устроен так же: *«rollback can be thought of as saving the game at the start of each
statement that interacts with the user, and loading saves when the user rolls back»*.
`RollbackLog` — двусвязный список `RollbackEntry`, каждая запись хранит **дельту** изменений
store с прошлого чекпоинта, а не полный снимок. Так rollback остаётся дешёвым по памяти.

Ограничение: не всё сериализуемо. Не пиклятся Render-объекты, итераторы и генераторы,
корутины, файловые хендлы, сокеты, лямбды и вложенные функции. Такой код оборачивают в
`python hide`, чтобы он остался вне системы сейвов.

Вывод: **план был неправ, заложив реплей.** Реплей выглядит экономнее (сейв в четыре поля),
но требует детерминированности всех команд и разваливается на `jump`/`call` из середины
чужой сцены — потому что путь исполнения восстановить нельзя. Ren'Py от этой идеи отказался,
и Pixi'VN с ink пришли к тому же: снапшот состояния.

### preferences — отдельно от сейва

Настройки живут вне сейвов и вне прохождений: `preferences.text_cps`, `preferences.afm_time`
и `afm_enable` (авточтение), микшеры громкости по каналам (main / music / sound / voice),
`skip_unseen` и `skip_after_choices`, `preferences.transitions`, `fullscreen`, `language`.

Изменил игрок скорость на 50 — она останется 50 в следующих запусках, независимо от сейвов.
В брифе `settings` уже отделены от сохраняемых данных — это совпадает со стандартом.

### persistent — третий вид данных

Кроме сейвов и настроек есть `persistent`: данные, не привязанные к точке в игре. Хранит
прочитанные реплики (на этом работает «пропустить прочитанное»), достижения, разблокированный
контент, галерею, отметки прогресса. Сохраняется при выходе или по `renpy.save_persistent()`.

Итого **три независимых хранилища**: сейв (точка в игре), preferences (настройки игрока),
persistent (глобальный прогресс). У нас в плане было два. Третье понадобится, как только
появится «пропустить прочитанное» или достижения.

### Аудио: каналы

Обычные каналы играют по одному файлу и поддерживают очередь: `music` — фоновая музыка,
`sound` — эффекты, плюс кастомные через `register_channel()`. Особые: `audio` (несколько
файлов разом, без очереди и стопа), `voice` (управляется системой озвучки).

Операторы: `play` (перебивает канал), `stop`, `queue` (в очередь после текущего).
Опции `play`: `fadein` / `fadeout`, `loop` / `noloop`, `volume`, и очень полезный
**`if_changed`** — не перезапускать трек, если он уже играет. Ровно то, что нужно, чтобы
музыка не начиналась с нуля при загрузке сейва в той же сцене.

Итоговая громкость — произведение: главный микшер × микшер канала × громкость канала ×
амплитуда трека × амплитуда из имени файла.

### gui.rpy — файл дизайн-токенов

Вся тема UI собрана в один файл переменных: `gui.accent_color`, `gui.idle_color`,
`gui.hover_color`, `gui.text_color`, `gui.text_font`, `gui.text_size`, `gui.name_text_size`,
`gui.textbox_height`, `gui.dialogue_ypos`, `gui.name_xpos`, `gui.button_height`,
`gui.slider_size`, границы и тайлинг рамок.

То есть Ren'Py пришёл к тому же, что мы решили сделать через `ThemeProvider` + токены —
причём с полезной подсказкой, какие именно токены нужны новелле: высота текстбокса,
позиция реплики, позиция имени, размер имени отдельно от размера реплики.

### Screens — декларативный UI, отделённый от скрипта

Screens — это UI-слой: диалоговое окно, меню, кнопки, HUD. Всё, кроме фонов и спрайтов,
которыми управляет скрипт через `scene` / `show` / `hide`.

Screens **обновляются в начале каждого interaction** — то есть это реактивный слой над
состоянием игры. Данные достаются по цепочке областей видимости: локальные переменные →
переменные screen'а → параметры screen'а (только чтение) → глобальный store.

Стандартный набор: `say`, `choice`, `main_menu`, `preferences`, `save` / `load`, `quick_menu`.

Для нас это ровно React: компоненты реагируют на observable-состояние. Полезен именно
**список стандартных экранов** — это чек-лист того, что новелла обязана иметь.

### Ожидаемый игроком набор функций

Из разбора Ren'Py и Monogatari складывается общий список того, что игрок жанра считает
само собой разумеющимся:

- **skip** — пропуск, обычно на Ctrl, отдельно «пропускать только прочитанное»;
- **auto** — авточтение с настраиваемой задержкой;
- **backlog / история** — лог прочитанных реплик с прокруткой;
- **rollback / назад** — вернуться на реплику назад;
- **quick save / quick load**;
- слоты сохранений, часто со скриншотом кадра;
- настройки: скорость текста, скорость авточтения, громкости по каналам, полноэкранный режим;
- ненавязчивый quick-menu вдоль нижнего края.

В 0.1 из этого сознательно берём только настройки. Остальное — список на потом, но
состояние стоит проектировать так, чтобы лог и rollback добавлялись без переделки.

## Что сознательно не берём

- **Свой скриптовый язык и парсер.** Бриф это прямо запрещает, и TS-модули с типами дают
  автокомплит, которого у `.rpy` нет.
- **NVL-режим.** Нам нужен ADV.
- **Контексты как отдельная сущность.** Нужны, когда UI может запустить вложенное
  прохождение (галерея, реплей сцены). Пока нет.
- **Дельты в rollback.** Ren'Py экономит память на дельтах, потому что состояние Python
  неограниченно. У нас кадр — это несколько полей plain data; при необходимости rollback
  хранит N последних снапшотов целиком.
- **Система screens как отдельный DSL.** У нас есть React, это тот же слой.
- **`transient` слой.** Артефакт устройства Ren'Py, в React не нужен.

## Находки по остальным решениям

### Pixi'VN

Единственный движок в нашем стеке: TypeScript, npm-пакет `@drincs/pixi-vn`, UI отдаётся
React или Vue, встроенного UI нет вообще. Подсистемы разведены на **narration, canvas, sound,
storage, save** — то же деление, что у нас в `engine/`. Нарратив описан через **labels и
steps**, точка входа `Game.start()` с меткой и начальными переменными. Поддерживает ink как
альтернативный язык сценария.

Сейв: `Game.exportGameState()` отдаёт состояние целиком, `Game.restoreGameState(data, navigate)`
восстанавливает — то есть снапшот, третье независимое подтверждение модели.

Почему не берём как зависимость: LGPL-2.1, ~132 звезды и один мейнтейнер, плюс он тянет
PixiJS, который брифом отложен. Но раскладку подсистем и терминологию (labels / steps /
storage) он подтверждает.

### Monogatari

Самый популярный веб-движок жанра (MIT, ~868 звёзд). Философия: *«Your visual novel is a web
page first and a game later»* — по духу совпадает с нашим брифом. Расширяется через **actions,
components и декораторы** на кастомных веб-компонентах, сценарий — простой список в
`script.js`.

Из коробки: сейв/загрузка со скриншотами слотов, rollback, auto-play, skip текста и лог
диалога. То есть полный ожидаемый набор — полезен как чек-лист.

Архитектура на web-components под React+MobX не переносится. Из зависимостей забирать нечего:
`animate.css`, `mousetrap`, `luxon`, `@tsparticles`, `modern-screenshot`, свой форк
`random-js` (показательно: детерминированный рандом в движке новеллы — это осознанная
необходимость, если хочешь воспроизводимость).

### ink / inkjs

Не движок, а язык и рантайм нарратива. MIT, за ним коммерческие игры: Haven, Neo Cab,
Over the Alps, Falcon Age, Signs of the Sojourner.

Компилятор `inklecate` превращает `.ink` в JSON, рантайм его исполняет. API минимален:
`Continue()` — получить следующую порцию текста, `currentChoices` — доступные варианты,
`ChooseChoiceIndex()` — выбрать. Состояние истории сериализуется в JSON — сейв из коробки.

Цикл `Continue()` пока `canContinue`, затем показать `currentChoices` — это тот же цикл
interaction. Ещё одно подтверждение модели.

### RenJS V2

Порт идей Ren'Py в веб: TypeScript, Phaser, сценарий в YAML списком действий. ~112 звёзд,
последнее обновление — май 2025. Идея «сценарий как список действий» совпадает с нашей;
как живая зависимость рассматривать не стоит.

## Что меняется в плане

1. **Сейв: снапшот вместо реплея.** Ключевое решение в [plan-0.1.md](./plan-0.1.md)
   переписано. Требование детерминированности команд снимается.
2. **`scene` против `show` + автозамена по тегу.** Команда `background` разделяется.
3. **Реестр переменных с дефолтами** — механика `default` вместо одинокого поля `version`.
4. **howler.js** заменяет ручной `AudioService`; появляются каналы `music` / `sound` и
   `if_changed`.
5. **zod** на валидацию сейва.
6. **Токены темы** пополняются специфичными для новеллы величинами.
7. **`{done}`-приём**: резервировать финальную высоту реплики.
8. **Третье хранилище** (`persistent`) зафиксировано как известное будущее, не в 0.1.
9. **Терминология**: «блокирующая команда» → команда, требующая interaction.
