# Этап 5. Save / Load

**Цель:** пройти половину сцены, обновить страницу, «Продолжить» — то же место, тот же фон,
тот же персонаж в той же эмоции и позиции.

**Зависимости:** [этап 4](./04-choices.md).
**Контекст:** [plan-0.1.md → Сейв — это снапшот, а не реплей](../plan-0.1.md),
[engine-research.md → Сейв и rollback](../engine-research.md)

---

## Шаги

### 1. Формат

```ts
type SaveData = {
  version: 1;
  position: { sceneId: SceneId; step: number };
  vars: Record<VarName, VarValue>;
  stage: {
    background: BackgroundId | null;
    sprites: Array<{ tag: CharacterId; emotion: EmotionId; at: SpritePosition }>;
  };
  audio: { music: MusicId | null };   // заполняется на этапе 6
  savedAt: number;
};
```

`position` — объект, а не два поля, чтобы позже принять `callStack`, если появятся вызываемые
подсцены (у Ren'Py стек вызовов лежит в сейве).

### 2. Сохранение

- собрать снапшот из `GameStore` и `StageStore`
- **автосейв в начале каждой команды, требующей interaction** — дословно поведение Ren'Py:
  *«saving occurs at the start of a statement»*
- один слот. Множественные слоты — в будущем, как в брифе

### 3. Загрузка

1. прочитать и провалидировать
2. слить переменные: `{ ...variableDefaults, ...save.vars }` — переменная, появившаяся после
   того сейва, получит дефолт и не сломает игру (механика `default` из Ren'Py)
3. восстановить `stage`, `vars`, `audio`, поставить `position`
4. **выполнить одну команду** по индексу `position.step` — она гарантированно `say` или `choice`

Никакого проигрывания истории. Если команда на `step` вдруг оказалась мгновенной — это признак,
что контент изменился под старым сейвом: см. открытый вопрос про несовместимость.

### 4. Валидация через zod

- схема на `SaveData`, поле `version` — дискриминатор
- кривой или чужой JSON в localStorage **не должен ронять игру**: отбросить, залогировать,
  вести себя как будто сейва нет
- заготовка миграции: `version` меньше текущей → функция переноса

### 5. Хранилище

- `localStorage`, ключи с префиксом проекта (см. открытый вопрос)
- сейв и настройки — **разными ключами**: настройки переживают все прохождения, это отдельное
  хранилище по стандарту жанра
- обработать отказы: переполнение квоты, приватный режим браузера, отключённое хранилище.
  Игра должна остаться играбельной без сейвов

### 6. UI

- «Продолжить» в меню активна, когда валидный сейв есть
- при отсутствии или порче сейва — неактивна, без страшных сообщений

### 7. Тесты

- сохранение → загрузка даёт то же состояние (позиция, переменные, фон, спрайты)
- сейв без новой переменной: она получает дефолт
- сейв с мусором отбрасывается, игра стартует с нуля
- сейв с будущей `version` отбрасывается, а не интерпретируется наугад
- спрайты восстанавливаются в том же порядке, эмоции и позиции сохранены

## Открытые вопросы

- [ ] **(квиз)** Префикс ключей в localStorage. Предлагаю `ots:` — `ots:save:auto`,
      `ots:settings`. Короткий и не столкнётся ни с чем на том же origin.
- [ ] **(квиз)** Что делать, когда сейв несовместим с изменившимся контентом: пропала сцена,
      сдвинулись шаги, на `position.step` теперь мгновенная команда. Варианты: молча начать
      заново, показать сообщение «сейв устарел», или откатиться на начало сцены из сейва.
      Третий вариант мягче всего к игроку. Для пет-проекта, где контент правится постоянно,
      это будет случаться часто — стоит решить сразу.
- [ ] **(по факту)** Нужен ли throttle на автосейв. `localStorage` синхронный, но запись
      1–2 КБ на каждой реплике вряд ли заметна. Замерить и записать результат.
- [ ] **(доки)** Экспорт сейва в файл. Рекомендации по сейвам веб-игр советуют дать игроку
      способ забрать прогресс: очистка данных сайта убивает localStorage без предупреждения.
      В 0.1 не делаем, но зафиксировать как известное будущее.
- [ ] **(по факту)** Хранить ли в сейве отдельно «версию контента», чтобы отличать
      «формат сейва изменился» от «сценарий изменился». Это два разных случая, а `version`
      сейчас закрывает только первый.
